# 07. Модуль HOS (часы труда и отдыха)

По ТЗ: «учитывать режим труда и отдыха водителя при построении оптимальной „гармошки“
остановок — совмещение точек дозаправки с обязательными остановками на отдых». Вынесен за
рамки MVP, но в схеме уже заложен: у остановки есть поле `stop_type`, и тип `rest`
добавляется без миграции.

## Правила FMCSA, которые нужно моделировать

Для перевозки грузов (property-carrying), federal:

| Правило | Суть |
|---|---|
| **11 часов вождения** | Максимум за смену после 10 часов подряд отдыха |
| **14-часовое окно** | Вождение запрещено после 14 часов с начала смены. Окно **не останавливается** на перерывы — это ключевая деталь |
| **30-минутный перерыв** | После 8 часов суммарного вождения без перерыва |
| **10 часов отдыха** | Подряд, для сброса смены |
| **60/70 часов** | За 7 или 8 суток подряд (зависит от режима компании) |
| **34-часовой рестарт** | Сбрасывает недельный лимит |
| **Разделённый отдых** | Спальное место: 8+2 или 7+3 часа; более длинная часть не расходует 14-часовое окно |
| **Неблагоприятные условия** | +2 часа вождения при непредвиденной погоде/пробках |

Две ошибки, которые делают почти все, кто впервые это моделирует: считают, что 14-часовое
окно останавливается на перерыв (не останавливается), и забывают недельный лимит — а
именно он чаще всего становится узким местом в дальних рейсах.

## Как это считать

HOS — это **симулятор часов**, проходящий по маршруту:

```
состояние = (
    часы_вождения_в_смене,
    начало_14-часового_окна,
    часы_с_последнего_перерыва,
    часы_в_недельном_цикле,
)
```

Шагаем по сегментам маршрута, на каждом проверяем, не нарушен ли лимит, и при
необходимости вставляем остановку нужной длительности. Алгоритмически это просто; сложность
в аккуратности правил и в их сочетании со спальным местом.

## Совмещение с заправками: та самая «гармошка»

Здесь и находится инженерная суть модуля. Есть две системы ограничений:

- **топливные**: запас хода, резерв, цена — уже реализовано;
- **временные**: где обязан встать и на сколько.

Наивное решение — посчитать их по отдельности и наложить — даёт плохой ответ: водитель
встаёт на 10 часов в одном месте, а заправляется в другом, теряя час на лишний заезд.
Хороший план ставит обязательный отдых **на той же площадке**, где выгодно заправиться.

Формально это **задача о кратчайшем пути с ресурсными ограничениями**: минимизировать
стоимость топлива при ограничениях на топливо в баке и на часы. Точное решение —
labeling-алгоритм, где метка содержит и остаток топлива, и состояние часов.

Практичный путь в два этапа, который я бы рекомендовал для первой версии:

1. Симулятором часов определить **обязательные окна отдыха**: «между милей 520 и 610 нужно
   встать на 10 часов».
2. Внутри каждого окна выбрать площадку, максимизируя выгоду по топливу — переиспользуя уже
   написанный оптимизатор, добавив в кандидаты признак «здесь можно легально стоять».

Это не гарантирует оптимума, но даёт объяснимый результат и переиспользует существующее
ядро. Переходить к точному алгоритму имеет смысл, только если замеры покажут, что разрыв
с оптимумом существенный.

Важное свойство, которое стоит сохранить: **план обязан оставаться исполнимым**. Если
выбор дешёвой заправки означает нарушение часов — это не экономия, а штраф от DOT и
out-of-service. Ограничение по часам жёсткое, цена — мягкая.

## Парковка: практический блокер

Про это редко думают при проектировании, и зря: в США **дефицит мест для стоянки грузовиков**
— системная проблема. Рекомендация «встать на 10 часов на 580-й миле» бесполезна, если там
негде встать, а искать место водитель начинает, когда часы уже кончаются.

Источники данных о парковке:

- **TPIMS** — системы информирования о занятости парковок в ряде штатов Среднего Запада,
  часть данных публична;
- **511-сервисы штатов** — разного качества;
- **OSM** — теги `amenity=parking` с `hgv=yes`: покрытие неполное, но бесплатно, и мы уже
  умеем брать данные из OSM;
- коммерческие данные (Trucker Path и подобные) — платно.

Минимум для первой версии: труистопы из уже загруженного каталога заправок как места
стоянки (у крупных сетей парковка есть почти всегда). Занятость — следующий шаг.

## Откуда брать остаток часов

Без ELD придётся исходить из допущения «водитель начинает смену свежим», и это допущение
будет систематически неверным: рейс редко начинается в момент сброса часов.

С ELD (см. [04](04-eld-и-телеметрия.md)) доступен реальный остаток по всем трём лимитам, и
план становится применимым к сегодняшнему дню. **Поэтому HOS-модуль имеет смысл делать
после интеграции с ELD**, иначе получится красивый расчёт для идеального водителя.

## Юридическая оговорка

Система даёт рекомендации, ответственность за соблюдение часов — на водителе и перевозчике.
Это должно быть зафиксировано:

- в интерфейсе — видимой оговоркой рядом с планом;
- в договоре с клиентом;
- в данных — журналом того, какая рекомендация была выдана и на основании каких часов.

Последнее защищает обе стороны при разборе после инцидента.

## Оценка

| Работа | Недель |
|---|---|
| Симулятор часов + тесты по правилам FMCSA | 1–2 |
| Обязательные окна отдыха на маршруте | 1 |
| Совмещение с планом заправок, тип остановки `rest` | 1–2 |
| Данные о парковках и их пригодность | 1–2 |
| Остаток часов из ELD | 0.5 (при готовой интеграции) |
| Интерфейс: временная шкала рейса | 1 |

## Решения, которые нужно принять

1. **Режим 60/7 или 70/8** у заказчика.
2. **Используют ли водители разделённый отдых** — это заметно усложняет симулятор, и если
   не используют, первую версию можно сделать вдвое быстрее.
3. **Насколько важна парковка** — готов ли заказчик платить за коммерческие данные о
   занятости.
