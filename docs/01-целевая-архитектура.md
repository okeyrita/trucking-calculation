# 01. Целевая архитектура

Закрывает **риск №1 из ТЗ**: «не определена финальная архитектура объединения систем:
будет ли это дорожное приложение или отдельный центральный сервис».

## Ответ: центральный сервис, а не приложение в кабине

«Дорожное приложение» не может быть архитектурой этой системы, потому что задача — не
показать водителю подсказку, а **свести четыре чужие системы в одну картину**. Приложение
в кабине не может быть местом, где хранится история рейсов, где сверяются транзакции по
картам с планом, где считается P&L рейса и где сидит диспетчер. Оно может быть клиентом
такой системы — одним из нескольких.

Правильная форма:

```
                    ┌──────────────────────────────────────────┐
                    │        Центральный сервис (ядро)         │
   диспетчер ─────► │  канонические сущности, история, правила │
   (веб-SPA)        │  оптимизация, сверка план/факт, отчёты   │
                    └───┬───────┬────────┬────────┬────────────┘
   водитель ──────►     │       │        │        │
   (мобильный клиент)   │       │        │        │
                    ┌───▼──┐ ┌──▼───┐ ┌──▼────┐ ┌─▼──────────┐
                    │ CRM  │ │ ELD  │ │ карты │ │ факторинг  │
                    └──────┘ └──────┘ └───────┘ └────────────┘
                         внешние системы (чужие данные)
```

Ключевое свойство: **клиенты не ходят во внешние системы напрямую**. Мобильное приложение
водителя не знает, что существует Comdata, а диспетчерский интерфейс не знает про ELD-API.
Все они разговаривают только с ядром. Иначе логика интеграции размазывается по клиентам,
и каждая смена вендора превращается в релиз мобильного приложения.

## Стиль: модульный монолит, а не микросервисы

Соблазн распилить на сервисы по числу интеграций велик и ошибочен. Аргументы против на
этом этапе:

- **Одна команда.** Микросервисы решают проблему координации людей, а не кода. Пока
  команда меньше 8–10 человек, границы сервисов создают работу, а не экономят её.
- **Транзакционность важна.** Рейс, маршрут, план заправок и сверка транзакций должны быть
  согласованы. В монолите это одна транзакция Postgres, в микросервисах — сага с
  компенсациями.
- **Объёмы малы.** Сотни траков и тысячи рейсов в месяц — это нагрузка, которую один
  процесс Python переваривает не замечая.

Поэтому: **модульный монолит с явными границами**, готовыми стать сервисами, если
понадобится. Границы проводятся по внешним системам и по предметным областям, а не по
техническим слоям:

```
app/
  domain/          канонические сущности и правила (без I/O)
  modules/
    routing/       ← реализовано
    fuel/          ← реализовано частично (цены; нет транзакций)
    loads/         CRM: рейсы, клиенты, ставки
    telematics/    ELD: позиции, одометр, часы
    settlement/    факторинг: инвойсы, финансирование
    compliance/    HOS, IFTA-отчётность
  integrations/    адаптеры к конкретным вендорам (ACL)
  platform/        auth, tenancy, биллинг, очереди, наблюдаемость
```

Правило, которое стоит соблюдать с первого дня: **модули общаются через сервисные функции
и события, а не через чужие таблицы**. Если `settlement` читает таблицы `loads` напрямую,
через полгода их уже не разделить.

Единственный кандидат на вынос в отдельный сервис уже сейчас — **скраперы**. У них другой
профиль: браузер, большая память, длительные операции, нестабильность, другие требования
к сети. Они уже сидят в отдельном worker-контейнере, и это правильно.

## Канонические сущности

Каждый вендор описывает мир по-своему. Если эти описания попадут в ядро, система станет
заложником вендора. Поэтому — **канонический словарь**, в который переводится всё
входящее:

| Сущность | Смысл | Источник истины |
|---|---|---|
| `Carrier` (tenant) | Перевозчик — владелец данных | наша система |
| `Truck` | Тягач: габариты, бак, MPG | наша система, обогащается из ELD |
| `Driver` | Водитель, его часы и назначения | ELD |
| `Load` | Груз: клиент, ставка, точки, окна | CRM |
| `Trip` | Физическое перемещение, в т.ч. пустое | наша система |
| `RoutePlan` | Построенный маршрут и план заправок | наша система |
| `Position` | Точка трека с временем | ELD |
| `FuelTransaction` | Фактическая покупка топлива | топливная карта |
| `Invoice` | Счёт клиенту | CRM + факторинг |
| `Funding` | Выплата от фактора | факторинг |

**Источник истины** в таблице — не формальность. Для каждой сущности должно быть ровно
одно место, где правда, и остальные копии обязаны считаться кэшем. Самая частая ошибка в
таких федерациях — две системы, каждая из которых считает себя главной по грузам, и
ручное разгребание расхождений раз в неделю.

Наша система — источник истины ровно для трёх вещей: **рекомендаций, планов и результатов
сверки**. Всё остальное мы отражаем, а не порождаем.

## Потоки данных

Два принципиально разных режима, которые нельзя путать:

**Синхронный — только то, чего ждёт человек.** Построить маршрут, посчитать план заправок,
геокодировать адрес. Здесь важна задержка, здесь допустим прямой вызов внешнего API, здесь
нужен внятный таймаут и понятная ошибка. Сейчас это ~0.8 с на план, из них почти всё —
GraphHopper.

**Асинхронный — всё, что связано с чужими системами.** Забор цен, транзакций, позиций,
отправка инвойсов. Здесь важна не задержка, а надёжность: ретраи, идемпотентность,
устойчивость к тому, что вендор лежит два часа.

Между модулями — **доменные события**, а не прямые вызовы:

```
LoadAssigned      → построить план маршрута, зарезервировать окно
TripStarted       → начать слежение за позицией
PositionUpdated   → проверить отклонение от маршрута → возможно RerouteSuggested
FuelPurchased     → сверить с планом → RealizedSavingsComputed
LoadDelivered     → собрать документы → InvoiceSubmitted
InvoiceFunded     → закрыть P&L рейса
```

Транспорт для событий: **паттерн Outbox в Postgres** + Celery. События пишутся в таблицу в
той же транзакции, что и изменение данных, и отдельный воркер их разбирает. Это даёт
атомарность «изменил данные и отправил событие» без распределённых транзакций и без Kafka.

Kafka/NATS имеет смысл вводить, только когда появится реальная причина: несколько
потребителей одного потока, воспроизведение истории, объёмы телеметрии за пределами
Postgres. Для десятков траков это оверинжиниринг.

## Хранение

**PostgreSQL + PostGIS остаётся ядром.** Он уже держит геометрию, пространственные запросы
и реляционную часть — и справится со всем, кроме одного.

Исключение — **телеметрия позиций**. 50 траков × 1 точка в минуту = 72 тыс. точек в сутки,
26 млн в год. Обычная таблица это выдержит, но запросы по диапазонам начнут деградировать.
Варианты по возрастанию сложности:

1. **Партиционирование по месяцам** штатными средствами Postgres + агрессивная политика
   хранения (сырые точки 90 дней, дальше агрегаты). Хватает до сотен траков.
2. **TimescaleDB** (расширение к тому же Postgres) — гипертаблицы, автосжатие,
   непрерывные агрегаты. Ставится без смены СУБД, это главный аргумент.
3. Отдельное хранилище временных рядов — только при тысячах траков.

Рекомендация: начинать с (1), переходить к (2) по метрике, а не по предчувствию.

## Правила, которые дешевле принять сейчас

- **Время — всегда UTC в базе**, локальная зона только на отображение. Окна погрузки в
  рейсах — самый частый источник ошибок на час: у них есть своя зона, отличная от зоны
  водителя и от зоны офиса.
- **Единицы — американские в интерфейсе, но явно названные в коде.** `miles`, `gallons`,
  `mpg` в именах полей. Уже соблюдается.
- **Деньги — `Numeric`, не `float`.** Уже соблюдается.
- **Идемпотентность по `(provider, external_id)`** на каждой сущности, приходящей извне.
  Уже соблюдается для заправок и цен; то же нужно для транзакций, рейсов и позиций.
- **`tenant_id` на всех прикладных таблицах.** Уже соблюдается.
- **Никаких вендорских полей в доменных таблицах.** Сырой ответ вендора — в `JSONB`-поле
  `provider_meta` или в отдельной таблице сырых событий, доменные поля — отдельно.

## Решения, которые нужно принять

1. **Что такое «CRM» у заказчика** — коробочная TMS, самописное или таблицы? От этого
   зависит, интеграция это или импорт (см. [03](03-crm-и-грузы.md)).
2. **Нужен ли мобильный клиент водителю** и что он делает: только показывает план заправок
   или ещё собирает документы для факторинга. Второе сильно дороже и включает камеру,
   офлайн и загрузку файлов.
3. **Сколько траков в горизонте года.** От порядка величины зависит выбор хранения
   телеметрии и топология развёртывания, и почти ничего больше.
