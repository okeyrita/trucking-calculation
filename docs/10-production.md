# 10. Production-решение

Что нужно сделать, чтобы система из работающей на ноутбуке стала системой, на которой
зарабатывают. Документ отвечает на три вопроса: где это крутится, как понять, что оно
живо, и что делать, когда сломается.

## Три стадии, а не одна архитектура

Самая дорогая ошибка здесь — строить сразу под тысячу клиентов. Kubernetes, очереди
сообщений и мультирегиональность на этапе «один перевозчик и 12 траков» съедят больше
времени, чем сам продукт.

| Стадия | Кто пользуется | Инфраструктура |
|---|---|---|
| **A. Внутренняя** | Сам заказчик, 1 тенант, до ~50 траков | Одна VM + managed Postgres |
| **B. Первые клиенты** | 3–20 перевозчиков | Контейнерная платформа + managed Postgres Multi-AZ |
| **C. SaaS** | Десятки и сотни | То же + автоскейл, изоляция очередей, зрелая наблюдаемость |

Переход между стадиями должен быть эволюцией конфигурации, а не переписыванием. Текущий
код это допускает: приложение stateless, состояние в Postgres и Redis, конфигурация из
окружения.

### Стадия A — то, что нужно сделать в первую очередь

```
  VM (2–4 vCPU, 8 ГБ)                    Managed PostgreSQL + PostGIS
  ├── api        (uvicorn, 2 воркера)    ├── ежедневные бэкапы + PITR
  ├── worker     (Celery)                └── приватная сеть, без публичного доступа
  ├── beat       (расписание)
  ├── frontend   (статика через Caddy)   Объектное хранилище (S3)
  └── Caddy      (TLS, реверс-прокси)    └── документы, выгрузки, бэкапы
       │
   Redis (тот же хост)
```

Отличия от текущего `docker-compose.yml`, которые обязательны перед выходом в прод:

1. **База — только управляемая** (RDS / Cloud SQL / Neon), не контейнер. Postgres в
   контейнере на той же машине — это потеря данных при первом же сбое диска.
2. **Фронтенд — статикой.** Сейчас в compose запускается dev-сервер Vite: он медленный,
   не кэширует и не предназначен для внешнего доступа. Нужен `npm run build` и раздача
   через Caddy/nginx.
3. **`--reload` у uvicorn убрать**, воркеров поставить по числу ядер.
4. **TLS** — Caddy получает сертификат Let's Encrypt автоматически, это одна строка.
5. **Секреты — не в `.env` на диске**, а из менеджера секретов при старте.
6. **Ограничение CORS** конкретным доменом вместо текущего regexp на localhost.

Это день работы, и он отделяет демо от системы, которой можно пользоваться.

### Стадия B — контейнерная платформа

Выбор по критерию «сколько времени уйдёт на эксплуатацию», а не по моде:

| Вариант | Плюс | Минус |
|---|---|---|
| **AWS ECS Fargate** | Нет узлов в обслуживании, интеграция с RDS/Secrets | Привязка к AWS |
| **Fly.io / Render / Railway** | Разворачивается за часы, дёшево на старте | Меньше контроля, лимиты |
| **Kubernetes (EKS/GKE)** | Гибкость, стандарт | Требует человека, который его знает |

Рекомендация: **ECS Fargate или Fly.io до тех пор, пока нет отдельного инженера
эксплуатации.** Kubernetes оправдан, когда появляются десятки сервисов или требования
клиентов к изоляции — а не раньше.

Отдельная деталь именно этого проекта: **воркер со скрапером требует особого обращения**.
Ему нужен браузер (образ ~2.5 ГБ), много памяти, длинные таймауты, и он периодически
подвисает. Его следует вынести в отдельный сервис/пул с собственными лимитами и
перезапуском по расписанию — тогда его проблемы не задевают обновление цен и построение
маршрутов.

## База данных

**Пул соединений — первое, что сломается под нагрузкой.** Асинхронный SQLAlchemy легко
открывает больше соединений, чем выдерживает Postgres. Нужен **PgBouncer** в режиме
транзакций между приложением и базой.

Важная тонкость: в transaction pooling не работают подготовленные выражения asyncpg. Для
SQLAlchemy это лечится параметром `statement_cache_size=0` в строке подключения — если этого
не сделать, ошибки появятся под нагрузкой и будут выглядеть необъяснимо.

**Миграции.** Уже используется Alembic, и на реальной базе проверено, что миграция
соответствует моделям (`alembic check`). Для прода добавить:

- прогон `alembic check` **в CI** — это ловит расхождение схемы и моделей до деплоя;
- правило совместимости: сначала выкатывается код, работающий и со старой, и с новой
  схемой, потом схема, потом уборка. Колонки не переименовываются одним шагом;
- запрет блокирующих операций на больших таблицах в рабочее время (`ALTER TABLE … ADD
  COLUMN NOT NULL DEFAULT` на миллионах строк);
- `lock_timeout` и `statement_timeout` на миграционной сессии, чтобы застрявшая миграция
  не положила систему.

**Бэкапы.** Автоматические ежедневные + PITR у управляемой базы. И главное: **восстановление
надо репетировать**. Бэкап, из которого ни разу не восстанавливались, бэкапом не является.
Раз в квартал — учебное восстановление в отдельную базу с замером времени.

## Наблюдаемость

Без этого нельзя запускаться, потому что большая часть данных приходит из чужих систем, и
их поломки не выглядят как ошибки вашего кода.

**Логи** — структурированные JSON (structlog), с `tenant_id`, `route_id`, `provider` и
идентификатором запроса в каждой записи. Секреты и персональные данные в логи не попадают
никогда.

**Трассировка** — OpenTelemetry. В этом проекте особенно полезна: запрос плана — это цепочка
«геокодирование → маршрутизация → коридорный запрос PostGIS → оптимизация → сохранение», и
без трассировки непонятно, какое звено тормозит.

**Метрики** — Prometheus + Grafana либо облачный эквивалент. Кроме стандартных четырёх
сигналов нужны предметные:

| Метрика | Почему критична |
|---|---|
| **Возраст самой свежей цены** | План на позавчерашних ценах хуже отказа. Алерт при > 36 ч |
| Состояние сессий скраперов | `needs_login` = интеграция стоит, и об этом узнают не от клиента |
| Доля неисполнимых планов | Резкий рост = проблема с данными о заправках или с маршрутами |
| Доля маршрутов с `truck_legal = false` | Сейчас это 100%; должно стать сигналом, а не нормой |
| Ошибки и стоимость внешних API | Прямые деньги; на тенанта — юнит-экономика |
| Задержка построения плана, p95 | Сейчас ~0.8 с, почти всё — внешний маршрутизатор |

**Ошибки** — Sentry с группировкой по тенанту.

Отдельно стоит выделить класс «тихих» поломок, о котором сказано в
[02](02-принципы-интеграций.md): вендор изменил формат, данные приходят, но неправильные.
Ловится проверками правдоподобия (цена дизеля вне $2–10, объём выгрузки упал вдвое), и эти
проверки должны поднимать алерт, а не писать в лог.

## Оповещения и дежурство

Будить человека можно только тем, что требует немедленного действия:

| Событие | Реакция |
|---|---|
| API недоступен, ошибки > 5% | Разбудить |
| База недоступна / место на диске | Разбудить |
| Цены не обновлялись > 36 ч | Утром, но обязательно |
| Скраперу нужен логин | Утром, задача человеку |
| Квота маршрутизатора на исходе | Утром |
| Единичные ошибки вендора | Только в дашборд |

## CI/CD

Минимальный конвейер, который стоит настроить сразу (GitHub Actions):

```
на PR:   ruff → pytest (офлайн) → pytest (с PostGIS в сервисе) →
         alembic check → tsc --noEmit → npm run build → сборка образа
на main: деплой в staging → смоук-тесты → ручное подтверждение → прод
```

Смоук-тест после деплоя: `/health` отвечает `ok`, план по эталонному плечу строится и даёт
ожидаемое число остановок. Это ловит «задеплоили, а база не мигрировала» за минуту.

Обязательно: **автоматическое сканирование зависимостей** (Dependabot/Renovate) и образов
(Trivy). В образе с Playwright и Chromium уязвимости появляются регулярно.

## Безопасность

- TLS везде, HSTS, база без публичного адреса.
- Роль приложения в БД — без `BYPASSRLS` и без права менять схему (см.
  [08](08-мультитенантность-и-монетизация.md)).
- Ограничение частоты запросов на уровне прокси и на уровне тенанта.
- Ротация секретов и журнал доступа к ним.
- **Журнал действий пользователей** — кто смотрел и менял данные. При мультитенантности это
  не роскошь, а обязательное условие доверия.
- Изоляция скрапера: он ходит на внешние сайты с чужими учётными данными, и его лучше
  держать в отдельном сетевом сегменте с ограниченным исходящим трафиком.

Про персональные данные: местоположение водителей и их рабочие часы — чувствительные
данные. Нужны сроки хранения, ограничение доступа по ролям и договорная фиксация ролей
контролёра и обработчика. При продаже более крупным парками рано или поздно спросят SOC 2 —
свидетельства для него (журналы доступа, ревью прав, управление изменениями) дешевле
собирать с самого начала, чем воспроизводить задним числом.

## Стоимость и как её снижать

Переменная часть в этом продукте необычная: **платит не сервер, а внешние API**.

| Статья | Порядок |
|---|---|
| Managed Postgres | $50–200/мес на стадиях A–B |
| Вычисления (контейнеры) | $50–150/мес |
| **Маршрутизация** | Зависит от числа планов; на платных truck-тарифах это главная статья |
| Хранилище, логи, мониторинг | $20–100/мес |

Три приёма, которые реально снижают счёт:

1. **Кэш маршрутов** по ключу (откуда, куда, габариты, провайдер). Плечи повторяются
   постоянно — Даллас–Чикаго строится снова и снова. Самый прямой способ.
2. **Дедупликация одинаковых запросов** в пределах короткого окна.
3. **Пересчёт плана без пересчёта маршрута**: смена режима IFTA или стартового остатка
   топлива не меняет геометрию. Сейчас каждый такой запрос идёт в маршрутизатор заново —
   это очевидная оптимизация, и она же первая по эффекту.

Последний пункт стоит реализовать до выхода в прод: он сокращает число платных вызовов в
разы при работе диспетчера, который перебирает варианты.

## Что делать, когда сломается

Аварийные сценарии, для которых нужен заранее написанный порядок действий:

**Маршрутизатор недоступен.** Отдавать кэшированный маршрут с пометкой о возрасте; если
кэша нет — честная ошибка. Молча подставлять неточный маршрут нельзя.

**Цены устарели.** Строить план, но выводить предупреждение с датой цен. При возрасте свыше
порога — требовать явного подтверждения от пользователя.

**Сессия скрапера истекла.** Статус `needs_login`, уведомление, работа на предыдущих ценах.
Уже реализовано и проверено.

**Квота внешнего API исчерпана.** Деградация: отдавать кэш, ставить запросы в очередь,
предупредить клиента. Не падать.

**Неудачная миграция.** Откат по подготовленному `downgrade` либо восстановление из PITR.
Порядок действий должен быть записан и проверен на учебной тревоге, а не сочиняться в
момент инцидента.

## Пробелы, которые стоит закрыть до первого платящего клиента

Честный список того, чего в текущем коде нет:

1. Сборка фронтенда для прода вместо dev-сервера Vite.
2. Аутентификация и авторизация — сейчас API полностью открыт.
3. RLS и реальная мультитенантность (см. [08](08-мультитенантность-и-монетизация.md)).
4. PgBouncer и настройка пула.
5. Кэш маршрутов и разделение «пересчитать план» / «построить маршрут».
6. Структурированные логи, метрики, трассировка, Sentry.
7. Ограничение частоты запросов.
8. Журнал действий пользователей.
9. Бэкапы с проверенным восстановлением.
10. CI/CD с прогоном тестов на PostGIS и `alembic check`.

Пункты 1–4 — обязательный минимум; 5–7 — до первых внешних пользователей; 8–10 — до продажи
как SaaS.
