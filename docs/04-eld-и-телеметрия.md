# 04. ELD и телеметрия

По ТЗ: «GPS-координаты трака, скорость, контроль часов труда/отдыха водителя (HOS). Есть
API (без 2FA)».

Это самая недооценённая интеграция в проекте. В ТЗ она описана как источник координат, но
её главная ценность в другом: **ELD превращает предположения топливной модели в
измерения**.

## Что меняется, когда появляется ELD

Сейчас модуль топлива стоит на двух допущениях: расход 6.5 MPG и бак, наполнение которого
мы считаем виртуально. Оба берутся из профиля трака и не проверяются. ELD даёт:

| Данные | Что чинит |
|---|---|
| **Уровень топлива из ECU** (%) | Виртуальный бак становится измеренным. Исчезает накопление ошибки: сейчас после двух заправок расчётный остаток может разойтись с реальным на десятки галлонов |
| **Фактический MPG** по одометру и заправкам | Расход перестаёт быть константой. Реальный разброс между траками и сезонами — 5.5–7.5, то есть до 25%. Это прямо переносится в ошибку плана |
| Одометр | Сверка наших миль с фактическими, отладка расхождений с CRM |
| Позиция и время | Автоматический триггер перестроения маршрута, а не ручной вызов |
| Часы HOS | Реальный остаток часов вместо допущения «водитель свежий» (см. [07](07-модуль-hos.md)) |

Ошибка в 25% по расходу значит, что план заправок может промахнуться мимо станции, и трак
доедет до неё на резерве или не доедет. Никакая оптимизация цены этого не компенсирует.
Поэтому по влиянию на качество продукта ELD стоит выше, чем CRM и факторинг.

## Выбор провайдера

Заказчик уже с кем-то работает, и менять ELD ради интеграции никто не будет — так что это
не выбор, а адаптация. Но знать ландшафт полезно:

| Провайдер | Особенности для интеграции |
|---|---|
| **Samsara** | Развитый REST API, вебхуки, хорошая документация. Лидер по оценкам рынка |
| **Motive** (ex-KeepTruckin) | REST API + вебхуки, помесячные контракты — часто у малых парков |
| **Geotab** | Крупнейшая экосистема интеграций (430+ решений), SDK, MyGeotab API |
| **Omnitracs, EROAD, Verizon Connect** | Корпоративный сегмент, интеграция тяжелее |

ТЗ упоминает «Lockbook/аналог» — такого известного бренда нет, скорее всего это искажение
названия. **Первым делом нужно выяснить фактического провайдера**: от него зависит,
доступны ли вебхуки и данные ECU, а без последних главная ценность интеграции теряется.

Ключевой вопрос при уточнении: **есть ли доступ к уровню топлива и расходу через API**, а
не только к позициям. Не все тарифы и не все установки это дают: данные ECU идут через
J1939, и если устройство подключено только к диагностическому разъёму без нужных PGN, их
просто нет.

## Объёмы и хранение

Простая арифметика, определяющая архитектуру хранения:

```
50 траков × 1 точка/мин × 60 × 24  = 72 000 точек/сутки
                                    ≈ 26 млн точек/год
500 траков                          ≈ 260 млн точек/год
```

Рекомендация из [01](01-целевая-архитектура.md): партиционирование по месяцам в том же
Postgres, переход на TimescaleDB по метрике. Политика хранения важнее выбора технологии:

- **сырые точки** — 90 дней;
- **упрощённый трек рейса** (Douglas-Peucker, как уже сделано для маршрутов) — бессрочно,
  он нужен для истории и разбора;
- **агрегаты по штатам и суткам** — бессрочно, это основа IFTA-отчётности.

Хранить сырую секундную телеметрию годами — распространённая ошибка: объём растёт, а
пользуются ей раз в год при разборе ДТП, для чего достаточно упрощённого трека.

## Как забирать

**Вебхуки** — для событий: смена статуса водителя, начало/конец рейса, аварийные события.

**Опрос** — для позиций: раз в 1–5 минут пачкой по всему парку одним запросом. Поштучный
опрос по траку упирается в лимиты API и не масштабируется.

**Ночная сверка** — обязательна, как и везде (см. [02](02-принципы-интеграций.md)).

Частота опроса — это компромисс между лимитами API и качеством. Для перестроения маршрута
хватает 5 минут; для «где трак прямо сейчас» на карте диспетчера нужна минута.

## Что делать с позициями

**Привязка к маршруту (map matching).** Сырая точка GPS сама по себе бесполезна — нужно
понимать, где трак относительно плана: пройдено миль, отклонение, опоздание. Практичный
путь: спроецировать точку на сохранённую геометрию маршрута через `ST_LineLocatePoint` —
ровно тот же приём, что уже используется для привязки заправок к коридору. Полноценный
map matching (Valhalla Meili, OSRM match) нужен только для восстановления трека по редким
точкам.

**Обнаружение отклонения.** Если трак дальше N миль от плановой линии дольше M минут —
маршрут изменился: объезд, пробка, водитель поехал иначе. Это триггер к автоматическому
перестроению, эндпоинт для которого уже есть.

**Определение стоянок.** Скорость около нуля дольше 15 минут — остановка. Сопоставление
стоянок с планом заправок и с обязательным отдыхом закрывает вопрос «выполняется ли план»
без единого вопроса водителю.

## Приватность

Данные о местоположении водителя — персональные данные, и относиться к ним надо
соответственно, особенно при продаже как SaaS:

- срок хранения должен быть обоснован, а не «навсегда на всякий случай»;
- доступ — по ролям: диспетчеру нужен его парк, а не все тенанты;
- журнал доступа: кто и когда смотрел трек конкретного водителя;
- в Калифорнии применим CCPA/CPRA, а часть перевозчиков работает с калифорнийскими
  клиентами;
- в договоре с клиентом-перевозчиком нужно зафиксировать, что контролёр данных — он, а вы
  обработчик.

## Оценка

| Работа | Недель |
|---|---|
| `TelematicsProvider` + адаптер к конкретному ELD | 1–2 |
| Хранение позиций, партиционирование, политика хранения | 1 |
| Привязка к маршруту, отклонения, автоперестроение | 1–2 |
| Фактический MPG и уровень бака в модели топлива | 1 |
| Часы HOS в модель (см. [07](07-модуль-hos.md)) | — |

## Решения, которые нужно принять

1. **Какой ELD фактически стоит** и какой у него тариф.
2. **Доступны ли данные ECU** — уровень топлива и расход. Если нет, стоит ли менять
   конфигурацию устройств: это главный источник точности.
3. **Частота опроса позиций** — от неё зависит и стоимость, и качество слежения.
4. **Срок хранения телеметрии** — решение бизнеса и юриста, а не разработчика.
