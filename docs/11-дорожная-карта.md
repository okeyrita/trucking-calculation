# 11. Дорожная карта

Очередность выбрана не по объёму работ, а по двум критериям: **что разблокирует следующее**
и **что раньше начинает приносить деньги**. Оценки — человеко-недели одного разработчика,
без учёта ожидания доступов.

## Что уже есть

Модуль маршрутизации и контроля топлива: truck-friendly маршрут за адаптером, оптимальный
план заправок с проверкой против точного алгоритма, виртуальный бак, переключатель IFTA,
разбивка по штатам, история, перестроение в пути, SPA на трёх языках, 70 тестов.

Два ограничения, из-за которых это пока демонстрация, а не рабочий инструмент: маршруты
строятся не truck-профилем, а цены не контрактные.

## Фаза 1. Сделать цифры настоящими (3–5 недель)

Без неё всё остальное строится на песке: нельзя продавать экономию, посчитанную по
смоделированным ценам на маршруте, который может завести под низкий мост.

| Работа | Недель | Блокер |
|---|---|---|
| Truck-маршрутизация: выбрать провайдера и подключить | 1 | Решение о бюджете |
| Контрактные цены: API или скрапер кабинета | 1–2 | **Доступы от заказчика** |
| Модель цены (cost plus / retail minus) | 1 | Условия контракта |
| Прод-минимум: сборка фронта, TLS, managed БД, секреты | 1 | — |

**Готово, когда:** диспетчер строит маршрут, который можно отдать водителю, и видит цены
своей карты.

## Фаза 2. Доказать экономию (3–5 недель)

Переводит продукт из «система советует» в «система сэкономила столько-то».

| Работа | Недель |
|---|---|
| Транзакции по топливным картам | 1–2 |
| Сверка план/факт, реализованная экономия | 1–2 |
| Отчёт об отклонениях и их стоимости | 1 |

**Готово, когда:** владелец открывает отчёт за месяц и видит сумму сэкономленного и сумму,
потерянную на отклонениях от плана. Это же — главный инструмент продаж.

## Фаза 3. Убрать допущения (4–6 недель)

Точность плана упирается в два числа, которые сейчас берутся из настроек: расход и остаток
в баке. ELD заменяет их измерениями.

| Работа | Недель |
|---|---|
| Интеграция с ELD: позиции, одометр, часы | 1–2 |
| Фактический MPG и уровень бака в модели | 1 |
| Хранение телеметрии, политика хранения | 1 |
| Отклонение от маршрута → автоперестроение | 1–2 |

**Готово, когда:** план строится на реальном расходе конкретного трака, а не на константе
6.5, и система сама предлагает перестроение при отклонении.

## Фаза 4. Собрать P&L рейса (4–7 недель)

Момент, когда четыре системы превращаются в одну картину.

| Работа | Недель |
|---|---|
| CRM: грузы, рейсы, пустые пробеги | 2–3 |
| Факторинг: инвойсы и статусы финансирования | 1–2 |
| P&L на рейс, отчёты | 1–2 |

**Готово, когда:** по каждому рейсу видно ставку, топливо, пустые мили, комиссию фактора и
маржу.

## Фаза 5. HOS (4–7 недель)

Ставится после ELD осознанно: без реального остатка часов расчёт будет для идеального
водителя.

| Работа | Недель |
|---|---|
| Симулятор часов FMCSA | 1–2 |
| Совмещение отдыха с заправками | 1–2 |
| Парковки | 1–2 |
| Временная шкала рейса в интерфейсе | 1 |

## Фаза 6. SaaS (8–12 недель)

| Работа | Недель |
|---|---|
| Аутентификация, роли, пользователи | 2–3 |
| RLS, разделение глобальных и тенантских данных | 2 |
| Доступы вендоров по тенантам, шифрование | 1 |
| Биллинг, тарифы, квоты | 2 |
| Онбординг + отчёт по исторической экономии | 2 |
| Наблюдаемость и регламенты продакшена | 2 |

**Готово, когда:** новый перевозчик регистрируется, подключает свои системы и получает
отчёт по своим данным без вашего участия.

## Зависимости

```
Фаза 1 ─┬─► Фаза 2 ──► Фаза 4 ──► Фаза 6
        └─► Фаза 3 ──► Фаза 5
```

Фазы 2 и 3 независимы и могут идти параллельно при двух разработчиках. Фаза 6 требует
завершённой фазы 2: продавать продукт, который не умеет показать экономию, нечем.

## Суммарно

| Сценарий | Недель | Комментарий |
|---|---|---|
| Рабочий инструмент для себя (фазы 1–2) | 6–10 | Минимум, окупающий себя |
| Полная система для себя (фазы 1–5) | 18–30 | Всё из ТЗ, кроме SaaS |
| Продукт на продажу (фазы 1–6) | 26–42 | Один разработчик |

**Главная оговорка.** Эти оценки — про разработку. На практике критический путь другой:
получение доступов к кабинетам вендоров, ответы на запросы API и согласования внутри
чужих компаний. Запрос на доступ к API топливной карты стоит отправить в первый день
работы над фазой 1, а не когда дойдут руки, — с большой вероятностью он и определит срок.

Второй фактор риска — уточнения от заказчика. Список вопросов собран в разделах «Решения,
которые нужно принять» каждого документа; на них стоит получить ответы одним пакетом, а не
по мере того, как каждый упрётся в очередной неизвестный параметр.
