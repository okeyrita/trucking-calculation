# Приблизительное ТЗ по разговору

Компания занимается грузоперевозками, работает по всей территории США с домашней локацией в Техасе. Грузоперевозки грузовиками Class 8, работают в режиме «свободного плавания» — уезжают с домашней локации на длительный срок и перемещаются по всей стране без фиксированного времени возврата.

## Бизнес-задача

Компания использует несколько разрозненных, не связанных друг с другом сервисов:

- Топливные карты
- CRM
- ELD-провайдер
- Факторинговая компания

**Проблема**: из-за отсутствия единой системы, невнимательности водителей и прочих внешних факторов при использовании топливных карт компания несёт перерасход от 500 до 1500 $ в месяц на одну машину.

**Причина**: цена на топливо в США сильно различается между штатами (разница может достигать 2 раз), и без подсказки водитель заправляется не в оптимальном месте.

**Цель проекта**: объединить разрозненные сервисы в единую систему и оптимизировать топливные расходы компании, начиная с модуля маршрутизации и контроля топлива.

## Целевая архитектура

Объединение сервисов из таблицы ниже в единую платформу.

| № | Система | Назначение | Доступность API |
|---|---|---|---|
| 1 | CRM-система | Учёт грузов: какая машина везла, клиент, даты забора/доставки, цена рейса, точка подачи машины (в т.ч. пустые пробеги) | Есть API |
| 2 | Топливная программа (fuel card provider) | Топливные карты, карта заправок с ценами именно по контракту компании (не розничная цена) | API может не быть доступен, вероятен скрапинг карты заправок с сайта; есть 2FA |
| 3 | ELD-провайдер | GPS-координаты трака, скорость, контроль часов труда/отдыха водителя (HOS) | Есть API (без 2FA, упоминался Lockbook/аналог) |
| 4 | Факторинговая компания | Финансовый посредник — выкупает дебиторку у компании и платит на следующий день (в отличие от клиентов, которые по закону могут платить до 45 дней) | Есть API, но с 2FA |

## Дополнительные требования к финальному продукту (за пределами MVP)

- **Мультитенантность**: система должна поддерживать множество изолированных аккаунтов/учёток клиентов, без пересечения данных между ними — поскольку в перспективе продукт планируется продавать как отдельный сервис другим компаниям (SaaS), а не только использовать внутри.
- **Монетизация**: конечная цель — продавать доступы как отдельный платный продукт (добавление платных пользователей/учёток).
- **Мультиязычность**: обязательна поддержка нескольких языков в интерфейсе — ~70% населения США не говорит на английском как на основном.

## Функционал MVP (первая часть — приоритет для старта работ)

### Модуль маршрутизации и контроля топлива

#### Truck-friendly маршрут

- Вход: точка старта и точка финиша на территории США.
- Построение реального дорожного маршрута с учётом ограничений для грузовиков большого класса (габариты, вес, запрещённые для грузовиков дороги и т.п.).
- Предполагаемые API для построения маршрута: HERE и GraphHopper (варианты предложены нейросетью заказчика, не являются жёстким требованием — решение по выбору API остаётся на этапе реализации).
- Заказчик подчеркнул, что «обычная» логистика маршрута (по расстоянию/времени) не проблема — с этим справляется даже Google Maps; ключевая ценность — слой топливной оптимизации сверху.

#### Контроль и оптимизация топлива

- Система должна сопоставлять построенный маршрут с координатами заправок, где действуют топливные карты компании (не любые заправки — только те, где карта принимается).
- Виртуальный топливный бак/виртуальный расход: поскольку у всех траков в среднем одинаковый запас хода и одинаковые технические характеристики, нужно ввести модель «виртуального бака» и виртуального расхода топлива для расчёта, когда и где потребуется дозаправка.
- **Важная особенность единиц измерения**: расход топлива в США считается в милях на галлон (miles per gallon, MPG) — то есть в «обратном» виде по сравнению с привычным литры/100км. Формула расчёта должна это учитывать.
- Результат работы алгоритма — список/маршрут рекомендованных заправок (там, где принимается топливная карта компании) с оптимальной ценой на топливо на пути следования, а не просто ближайших заправок.
- Учитывать необходимо и режим труда и отдыха водителя (HOS — Hours of Service) при построении оптимальной «гармошки» остановок (совмещение точек дозаправки с обязательными остановками на отдых).
- Гибкость маршрута: должна быть возможность адаптации при изменении условий (закрытые дороги, аварии, снег, лёд и т.п.) — то есть перестроение маршрута/рекомендаций заправок в реальном времени.

#### Учёт налогов IFTA

Нужен переключатель (on/off) для расчёта стоимости топлива:

- «чистая» цена на стелле (без вычета налога);
- цена с учётом налогового вычета IFTA (International Fuel Tax Agreement) — так как налог на топливо сильно различается между штатами.

#### История и хранение данных

Все построенные маршруты, геометрия трека, а также данные о фактической/расчётной экономии должны сохраняться в базу данных для последующего анализа и истории.

#### Работа с ценами на топливо (открытый вопрос — риск проекта)

- Заказчик не уверен, что провайдер топливных карт предоставит открытый API для получения цен на своих заправках.
- Если API недоступен — придётся парсить интерактивную карту заправок с сайта провайдера (карта с точками, при клике показывается цена по контракту компании). Цены на топливо в США обновляются один раз в сутки по стране.
- У сайта топливного провайдера и у сайта факторинговой компании стоит двухфакторная аутентификация (2FA) — это дополнительное технически усложняющее обстоятельство для автоматического сбора данных (нужно будет «пробивать» 2FA либо договариваться о выдаче доступа/API от провайдера).

**Пути решения:**

1. Написать провайдерам топливной программы и факторинговой компании с официальной или анонимной почты и запросить официальный доступ к API для экспорта нужных данных (некоторые компании предоставляют это по запросу, иногда платно, чтобы избежать нелегального скрапинга, который может «положить» их сайт).
2. Если добровольно не предоставят — писать скрапер для сбора данных с сайта.
3. Использовать логин/пароль заказчика для прямого доступа (заказчик готов передать доступы к части сайтов, где нет 2FA).

## Технический стек (предложен заказчиком через AI-инструмент, не финализирован)

- Python 3.12+ (FastAPI)
- PostgreSQL / PostGIS (для геоданных маршрутов)
- SQLAlchemy
- Celery (фоновые задачи — регулярное обновление цен на топливо)
- Docker
- HERE API / GraphHopper API (маршрутизация)

## Риски (не закрыты в разговоре, требуют уточнения)

1. Не определена финальная архитектура объединения систем: будет ли это «дорожное приложение» или отдельный центральный сервис, работающий с внешними веб-сайтами.
2. Доступность API топливного провайдера не подтверждена — ключевой риск проекта.

## Технический стек для модуля маршрутизации и контроля топлива — независимый разбор

## Ключевые технические развилки

Прежде чем выбирать конкретные инструменты, в задаче есть три критичных развилки, которые определяют весь стек:

**1. Провайдер маршрутизации для грузовиков.** Обычный Google Maps/OSM-роутинг не учитывает габаритные ограничения (высота мостов, вес, запрет на грузовики на отдельных дорогах). Рынок специализированных решений делится на три уровня: бесплатный self-hosted OSRM с truck-профилями (гибко, но нет юридической защиты и сертификации), коммерческие API уровня HERE или GraphHopper (готовые truck-профили "из коробки", у GraphHopper есть предустановленный truck-профиль с параметрами высоты/веса/осей) и профессиональные FHWA-сертифицированные системы типа PC*Miler, которые дают юридическую защиту при спорах по хазмат-перевозкам, но стоят $24k+/год против HERE $30k+/год при промышленной нагрузке. Для MVP разумно взять GraphHopper (self-hosted версия с открытым truck routing profile) или его облачный API — сертификация PC*

**2. Способ обхода 2FA у топливного провайдера и факторинговой компании.** Это не опциональная деталь — без решения этого вопроса модуль контроля топлива не заработает. Индустриальный стандарт для скрапинга аккаунтов с 2FA — не "взламывать" двухфакторку программно, а логиниться один раз вручную (пройдя 2FA), сохранить сессионное состояние (cookies/localStorage/JWT) через Playwright `storage_state`, и переиспользовать эту сессию до её истечения, с автоматическим повторным логином при протухании. Если у заказчика есть доступ к seed/secret ключу TOTP, можно пойти дальше и генерировать коды 2FA программно библиотекой `pyotp` в связке с Playwright, но это сложнее и менее надёжно. 

**3. Источник данных по IFTA-налогам.** Готовых открытых API по ставкам IFTA на рынке почти нет — компании типа Motive/Samsara держат это как часть закрытой B2B-подписки. Практичный путь для MVP — не интегрироваться со сторонним IFTA-сервисом, а держать справочник налоговых ставок по штатам в собственной БД (обновляется вручную/раз в квартал, IFTA-ставки публикуются централизованно и меняются нечасто) и считать вычет локально. 

## Рекомендуемый стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык/backend-фреймворк | Python 3.12+ / FastAPI (async) | Много I/O-bound работы (внешние API, скрапинг, БД) — asyncio даёт максимум пропускной способности без сложности Go; FastAPI даёт готовую OpenAPI-документацию, которая пригодится, когда продукт станет продаваться как SaaS с публичным API |
| Геоданные и хранение маршрутов | PostgreSQL + PostGIS | Единственный практичный стандарт для хранения геометрии (LineString/Point), пространственных индексов (сопоставление маршрута с координатами заправок) и spatial-запросов "заправки в буфере N км от трассы" |
| Truck-маршрутизация | GraphHopper (self-hosted, Docker-образ с truck-профилем на OSM-данных) | Открытый профиль truck со всеми нужными параметрами (высота, вес, оси) self-hosted снимает зависимость от лимитов платного API и позволяет тонко настраивать профиль под конкретные траки компании |
| Скрапинг сайтов с 2FA | Playwright (Python) + сохранение сессии через `storage_state`, планово обновляемое вручную/по расписанию | Единственный рабочий подход для аутентифицированного скрапинга за 2FA без нарушения защиты; headless-режим позволяет гонять это в фоне  |
| Фоновые задачи (обновление цен, повторный логин, парсинг) | Celery +  RabbitMQ | Обновление цен на топливо — регулярная периодическая задача (раз в сутки) плюс retry-логика при протухании сессии |
| IFTA-справочник | Собственная таблица ставок в PostgreSQL, без внешнего API | Готовых открытых API по ставкам IFTA практически нет на рынке  ставки стабильны и обновляются редко, поэтому ручное/полугодовое обновление справочника дешевле любой интеграции |
| Контейнеризация | Docker + docker-compose (для MVP), с прицелом на Kubernetes при росте до мультитенантного SaaS | Для одного клиента (себя) compose достаточен; при продаже как SaaS с изоляцией тенантов потребуется переход на K8s-неймспейсы или отдельные схемы БД на тенанта |
| Очередь для парсинга без 2FA-провайдеров (ELD, CRM) | httpx (async) напрямую, без Celery-обёртки на каждый запрос | Эти два сервиса дают чистый API без 2FA — не нужен браузер, достаточно асинхронного HTTP-клиента внутри тех же Celery-тасков |
| Фронтенд | React/Vue | Простейшая страница для отображения результата и ввода начальных параметров |
